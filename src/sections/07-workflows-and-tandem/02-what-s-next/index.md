## Greenfield, brownfield, bluefield

Rare was a **brownfield** project: an existing codebase with conventions, patterns, and decisions already baked in before you ever opened it. Your job was to discover what was already there and work within it. That's most professional software work. Very few developers get to start from an empty repo.

A **greenfield** project is the opposite: nothing exists yet. There's no `CLAUDE.md` to read, no established pattern to follow, no previous developer's decisions to reverse-engineer. You make the first architectural call, and it becomes the convention everything after it follows.

A **bluefield** project is a mix of both: some part of an existing system is being rebuilt or extended fresh, while the rest of that system is still running and still has to be respected. Replacing one legacy service while the rest of the app keeps serving traffic is a bluefield problem. It's a less standardized term than the other two, and you won't hear it as consistently across the industry, but the situation it describes (new work, old constraints, both at once) is common.

| | What it means | Where you've seen it |
|---|---|---|
| Brownfield | Existing codebase, existing conventions. You discover and follow before you change anything. | Rare, every module so far |
| Greenfield | No existing code. You set the first conventions, and `CLAUDE.md` starts blank. | Module VIII, below |
| Bluefield | New work built inside or alongside a system that's still running and still has constraints. | Adding a new service next to an existing one, or rewriting one feature while the rest of the app keeps working |

The habits from this course transfer to all three. What changes is where the constraints come from: someone else's decisions (brownfield), your own decisions made in real time (greenfield), or both at once (bluefield).
